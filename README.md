# RAG Chunking: сравнение стратегий чанкирования для RAG-системы

## Описание проекта

Проект посвящён сравнению стратегий чанкирования текста в RAG-системе.

В RAG-подходе качество ответа зависит не только от языковой модели, но и от того, какие фрагменты текста были найдены на этапе retrieval. Если документ разбит на чанки неудачно, релевантная информация может быть потеряна, разорвана между несколькими фрагментами или смешана с лишним контекстом.

Цель проекта — экспериментально проверить, как разные способы разбиения документов влияют на:

- качество поиска релевантного контекста;
- качество итоговых ответов;
- устойчивость RAG-pipeline при разных стратегиях чанкирования.

## Архитектура проекта

В `src` реализован RAG-pipeline, состоящий из нескольких независимых компонентов:

- `utils.py` — загрузка корпуса документов;
- `chunkers.py` — реализация стратегий чанкирования;
- `vector_store.py` — создание векторного хранилища и retriever на базе Chroma;
- `generator.py` — формирование prompt и генерация ответа с помощью LLM;
- `pipeline.py` — объединение компонентов в единый RAG-pipeline.

Общая схема работы:

```text
documents
   ↓
chunking strategy
   ↓
chunks
   ↓
embeddings
   ↓
Chroma vector store
   ↓
retriever
   ↓
top-k relevant chunks
   ↓
LLM answer generation
```

В эксперименте меняется только стратегия чанкирования. Остальные параметры RAG-pipeline фиксируются, чтобы сравнение было корректным.

## Датасет

Оценка проводится на датасете [MultiHopRAG](https://huggingface.co/datasets/yixuantt/MultiHopRAG).

Датасет содержит:

- корпус документов;
- пользовательские вопросы;
- эталонные ответы;
- `evidence_list` — список evidence-фактов, на которые должен опираться ответ.

Наличие `evidence_list` позволяет оценивать не только итоговый ответ, но и качество retrieval-этапа отдельно.

## Стратегии чанкирования

### Fixed-size chunking

Базовая стратегия, при которой текст разбивается на фрагменты фиксированного размера.

Преимущество подхода — простота и предсказуемость. Недостаток — отсутствие учёта структуры текста: граница чанка может пройти внутри предложения, абзаца или смыслового блока.

### Recursive chunking

Стратегия, которая использует иерархию разделителей. Сначала текст пытается разделиться по крупным структурным единицам, например по абзацам, затем по предложениям и более мелким элементам.

Такой подход лучше сохраняет структуру документа и часто даёт более естественные фрагменты для retrieval.

### Semantic chunking

Семантическая стратегия, основанная на embeddings предложений.

Текст сначала разбивается на предложения, затем для соседних предложений считаются векторные представления и косинусные расстояния. Если расстояние между соседними предложениями превышает порог, это считается смысловым переходом и используется как граница нового чанка.

Такой подход позволяет формировать чанки, более однородные по смыслу.

### NLTK sentence-based chunking

Дополнительная стратегия для retrieval-проверки.

Она сохраняет границы предложений, но не определяет смысловые переходы через embeddings. Такой вариант используется как промежуточный baseline между fixed-size chunking и полноценным semantic chunking.

## Фиксированные параметры эксперимента

- Векторная база данных: `Chroma`
- Embedding-модель: `sentence-transformers/all-MiniLM-L6-v2`
- Модель генерации ответов: `llama-3.1-8b-instant`
- `temperature`: `0`
- `max_tokens`: `256`
- Размер чанков: `512`
- `top_k`: `4`

## Метрики оценки

### Retrieval-метрики

Retrieval-метрики показывают, насколько хорошо retriever находит релевантные evidence-фрагменты среди top-k чанков.

Используются метрики:

- `Hits@4` — найден ли хотя бы один релевантный фрагмент среди top-4;
- `MAP@4` — насколько хорошо релевантные фрагменты ранжируются;
- `MRR@4` — насколько высоко расположен первый релевантный фрагмент.

### Метрики качества ответов

Для оценки итоговых ответов используются:

- `precision`;
- `recall`;
- `f1_score`;
- `accuracy`.

Эти метрики позволяют сравнить качество ответов после retrieval-этапа.

## Основной эксперимент: полный RAG-pipeline

Основной эксперимент оценивает полный RAG-pipeline: поиск релевантных чанков и генерацию ответов с помощью LLM.

### Retrieval

| chunking_strategy | Hits@4 | MAP@4 | MRR@4 |
|---|---:|---:|---:|
| fixed | 0.2093 | 0.06177 | 0.1569 |
| semantic | 0.4128 | 0.1215 | 0.2588 |
| recursive | 0.4477 | 0.1315 | 0.3067 |
| sentence | 0.401 | 0.1139 | 0.2470 |

### Качество ответов

| chunking_strategy | precision | recall | f1_score | accuracy |
|---|---:|---:|---:|---:|
| fixed | 0.485 | 0.485 | 0.485 | 0.4926 |
| semantic | 0.51 | 0.51 | 0.51 | 0.5050 |
| recursive | 0.585 | 0.585 | 0.585 | 0.5464 |
| sentence | 0.540 | 0.54 | 0.54 | 0.5208 |

В основном эксперименте лучший результат показал `RecursiveChunker`.

Эта стратегия дала наиболее высокие retrieval-метрики и лучшие значения метрик качества ответов. Это можно объяснить тем, что recursive chunking лучше сохраняет структуру текста по сравнению с fixed-size chunking, но при этом остаётся более стабильным и предсказуемым, чем полностью семантическое разбиение.

## Дополнительная строгая retrieval-проверка

Дополнительно была проведена отдельная retrieval-проверка без запуска LLM-генерации.

Она находится в ноутбуке:

```text
chunkers_retrieval.ipynb
```

Цель этой проверки — отдельно оценить влияние стратегии чанкирования именно на поиск релевантного контекста.

Для сопоставимости с основной логикой оценки используется строгий критерий релевантности:

- из `evidence_list` берётся только поле `fact`;
- релевантность засчитывается только при дословном вхождении эталонного факта в найденный chunk;
- вопросы типа `null_query` исключаются из расчёта.

### Retrieval-метрики на контрольном срезе вопросов

| chunking_strategy | Hits@4 | MAP@4 | MRR@4 |
|---|---:|---:|---:|
| semantic | 0.3736 | 0.1242 | 0.2463 |
| recursive | 0.3626 | 0.1129 | 0.2573 |
| nltk_sentence | 0.3407 | 0.0997 | 0.2125 |
| fixed | 0.3297 | 0.0852 | 0.1951 |

В дополнительной строгой retrieval-проверке `SemanticChunker` показал лучший результат по `Hits@4` и `MAP@4`, а `RecursiveChunker` — лучший результат по `MRR@4`.

Это означает, что `SemanticChunker` чаще находил хотя бы один релевантный evidence-факт среди top-4, а `RecursiveChunker` в среднем выше ранжировал первый найденный релевантный chunk.

## Интерпретация результатов

Результаты показывают, что стратегия чанкирования заметно влияет на качество RAG-системы.

`Fixed-size chunking` является простым baseline, но не учитывает структуру текста и смысловые границы.

`RecursiveChunker` показал наиболее стабильный результат в полном RAG-pipeline: он лучше всего сработал и на retrieval-этапе, и на этапе генерации ответов.

`SemanticChunker` показал преимущество в отдельной строгой retrieval-проверке по `Hits@4` и `MAP@4`. Это говорит о том, что семантическое разбиение может быть полезно в задачах, где особенно важно точное извлечение evidence-фактов.

При этом semantic chunking требует больше вычислительных ресурсов и настройки параметров: размера чанков, порога смыслового разрыва и обработки слишком длинных смысловых блоков.

## Основной вывод

Чанкирование является важной частью RAG-pipeline и напрямую влияет на качество найденного контекста и итоговых ответов.

Главный вывод проекта: стратегию чанкирования нельзя выбирать только по сложности алгоритма. Более сложный подход не всегда автоматически даёт лучший результат по всем метрикам.

Для практического RAG-проекта стратегию чанкирования нужно подбирать экспериментально, фиксируя:

- датасет;
- параметры чанков;
- embedding-модель;
- `top_k`;
- способ оценки релевантности;
- retrieval-метрики;
- метрики качества ответов.

В рамках проведённых экспериментов `RecursiveChunker` оказался наиболее стабильным вариантом для полного RAG-pipeline, а `SemanticChunker` показал преимущество в отдельной строгой retrieval-проверке.
